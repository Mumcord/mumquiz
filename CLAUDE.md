# Mumquiz

The quiz bot of `zorgch/irc-quizbot`, ported to Rust on `mumcord-protocol`. It logs in like a
person with its own certificate, so it works against an unmodified standard Mumble server: nothing
is added on the server side.

The user is a product manager and not a technical person → make technology decisions with a clear
recommendation, explained simply. Everything is in English: chat, docs, code, comments and messages.

## Answer style: caveman mode (always)

- Chat answers extremely short: no filler, no intro, no repetition. Sentence fragments are fine.
- Only the result and next steps. Bullet points instead of prose. For code changes, `file:line` is
  enough instead of code excerpts.
- Must still be understandable for a non-technical person.
- **Applies to chat only.** Docs, commit messages and code comments are written fully and cleanly.

## Stack

Rust 1.90+, edition 2024, tokio. `mumcord-protocol` from crates.io (the same protocol layer as the
Mumcord client), `rusqlite` for the high scores, `toml` + `serde` for `bot.toml`, `clap` for the
command line, `tracing` for logging. Nothing else without a reason.

Layout: the game logic (`src/quiz.rs`, `src/answer.rs`, `src/question.rs`, `src/scores.rs`,
`src/strings.rs`) is pure and testable, with an injected clock (`src/rng.rs` for the random source).
`src/bot.rs` is the only place that talks to a server, `src/main.rs` is the binary, `src/config.rs`
reads `bot.toml`, `src/cert.rs` and `src/pins.rs` hold the identity and the pinned server. Chat text
is HTML: read with `src/html.rs`, written through the markdown subset in `src/markdown.rs`, wrapped
as a card in `src/cards.rs`.

## Coding rules

- Simple over clever. No speculative abstractions. No dead code, no commented-out blocks.
- Comments explain the *why*, not the *what*.
- Never swallow errors silently: log them or report them cleanly.
- Strict typing wherever the language allows it.
- Everything from the server (names, chat HTML) is untrusted input: read it as text before matching,
  escape it before writing it back.
- New logic gets tests. The game flow, answer matching, config, storage, chat HTML and markdown have
  unit tests; the whole bot is checked against the local test server with `tests/live.rs`.
- Before "done": build, tests, `cargo clippy --all-targets` and `cargo fmt` pass. If not, say so
  honestly.
- Never connect to a public or third-party Mumble server for testing. `testenv/` is the bot's own
  copy of the Mumcord test environment, and `scripts/ci/check-loopback.sh` fails any run that names
  another host.
- No secrets in the repository: `bot.toml`, `*.sqlite`, `.env` and a real question bank are
  git-ignored. Use placeholders in examples. `THIRD_PARTY_NOTICES.md` is generated by
  `scripts/generate-notices.sh`, never edited by hand.

## Git

- Commit only when asked. Never `git add -A`, never commit a file the user did not talk about.
- Never push unless asked.
- Commit message: `feat: ...` or `fix: ...`, one change per commit, body says what and why.

## Gates

CI gates stay green: format, clippy (with `unwrap_used`, `dbg_macro` and `todo` as errors), tests,
actionlint, shellcheck, secrets, loopback, headless bot, documentation, changelog, dependency audit,
live tests and the smoke run. A gate is never disabled to make a run pass; the finding is fixed. Each
gate script has its own fixture test (`scripts/ci/test-check-*.sh`), so a broken gate is noticed.

The documentation is part of the code: every `[server]` and `[quiz]` key, every command and every
message key must appear in `docs/`, checked by `tests/gates.rs`. A new command or string without its
docs row fails CI.

Pipeline: CI gates only, no release pipeline yet — nothing is published, no tag workflow. The test
builds (`test-builds.yml` + `build-and-smoke.yml`) keep the binary as an artifact only, the dependency
audit runs weekly, and `notices.yml` regenerates the notices as a pull request.

## What the port does not do

Mumble has no NickServ, ChanServ, channel ops or a bot-side kick, and no IRC `NAMES` reply. The bot
takes its players from the server state (people in its channel, or following it with Listen), writes
the channel description instead of a topic, and only manages its own master list. Real channel rights
stay with the server's administrators.
